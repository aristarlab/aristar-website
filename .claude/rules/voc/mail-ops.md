# VOC 메일 운영 규칙

## 기반

Google Workspace(support@aristar.io) + Gmail API. 분류는 **Gmail 라벨**로 수행한다.
분류 기준의 단일 출처는 `ops/voc/taxonomy.yml`이다. 코드·문서에 기준을 중복 정의하지 않는다.

## 라벨 체계

```
사업/esay-memory-eng
사업/content-automation
사업/algo-trading
사업/미분류            ← 사업 식별 불가. 사람이 확인한다.
유형/문의  유형/버그  유형/환불  유형/제안  유형/제휴  유형/채용  유형/법무  유형/스팸
상태/신규  상태/대응중  상태/대기  상태/완료
```

메일 하나에 `사업/*` 1개, `유형/*` 1개 이상, `상태/*` 1개를 붙인다.

## 분류 순서

1. 제목의 `[<슬러그>]` 태그 → 해당 사업으로 확정 (서비스 페이지 CTA가 넣어준다)
2. 발신 도메인·수신 별칭 규칙 (`taxonomy.yml`의 `routes`)
3. 본문 키워드 규칙 (`taxonomy.yml`의 `keywords`)
4. 위 모두 불일치 → `사업/미분류` + `상태/신규`. **추측해서 사업을 배정하지 않는다.**

법무·개인정보 관련 문구(삭제 요청, 열람 요청, 분쟁, 내용증명)가 있으면 사업 라벨과 무관하게 `유형/법무`를 붙이고 경영지원(법무팀)에 올린다.

|---|---|

## 개인정보 — 반드시 지킨다

- **메일 본문·발신자 이름·메일 주소·전화번호를 저장소에 커밋하지 않는다.**
- `ops/voc/`에 두는 것: 분류 규칙, 집계 수치, 템플릿, 운영 절차.
- 리포트에 개인을 특정하지 않는다. "esay-memory-eng 버그 3건"처럼 집계로만 쓴다.
- 사례를 인용해야 하면 식별 정보를 지운 요약으로 바꿔 쓴다.
- 메일 삭제·일괄 아카이브는 CEO 승인 없이 실행하지 않는다. 라벨 부여는 승인 없이 가능하다.

## 주간 집계

`ops/voc/reports/YYYY-WW.md` — 사업별 건수, 유형 분포, SLA 초과 건수, 반복 이슈 상위 3건, 제품 개선 제안.
반복 이슈는 IT 또는 해당 사업 담당 본부로 이관하고 이관 사실을 기록한다.
