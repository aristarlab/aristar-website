CEO가 B안(색인)을 택했고 **`index.html`은 이미 B안으로 교체 완료**됐다. **시각 언어는 B안으로 대체됐고, 구조적 판단은 승계됐다** — 다크 타일 폐기, 성숙도≠중요도, 다이어그램 접근성 평탄화 회피(`<ol>` 실제 HTML 노출), 360px 대응, 하드코딩 색 제거라는 판단은 전부 유효하며 B안이 이를 더 강하게 충족한다.

## 0. 결론 요약

1. **제품 타일(현 색인 행)에서 `/슬러그` 서비스 페이지로의 링크가 여전히 비어 있다.** 결함 1은 **아직 해소되지 않았다** — 선행 조건(Next.js 전환, 서비스 페이지 존재)이 안 끝나 CEO 결정으로 연기됐다(취소가 아님). 세 사업 설명이 본문에 전부 들어가 있어 현재 페이지는 그 자체로 온전하다.
2. **성숙도 위계 문제는 다크 타일 폐기가 아니라 색인 행 구조 자체로 해소됐다.** 좌측 상태 열(`.status`)이 동일한 구조로 세 사업에 반복되므로, 성숙도 차이가 크기·명도·색의 차이로 번역되지 않는다. 신규 색 토큰 없이, 기존 확정 토큰(`--ink-mid`)만으로 끝난다.
3. 추상 제품 2개(콘텐츠 자동화·알고리즘 트레이딩)는 Stripe 축(레이블·방향·단계 번호·접근성 트리 노출)을 만족하는 설명형 목록으로 구현됐다 — 실제로는 SVG 없이 `<ol><li>` 단독으로, 더 단순한 형태로 요건을 충족했다(3절 참고).
4. 한국어 조판 보정은 자간 `clamp()` 보간식 없이 스케일 축소(44px 상한)로 해소됐다. 360px 대응은 `@media (max-width:380px)`로 이미 적용돼 있다.
5. 코드를 직접 읽은 결과 두 가지를 8절 실측 과제로 새로 올린다 — `--hairline`이 단계 번호(`.steps li::before`)의 텍스트 색으로 쓰인 점, `text-wrap:balance`가 확정 규칙(`web.md`)의 금지와 달리 두 곳에 쓰인 점.

## 1. 패턴별 4항목 명세

### 1-1. Apple — 전면 요소 정보량 상한

1. **패턴 이름**: 콘텐츠 블록 텍스트 요소 상한(사업명 + 짧은 설명 + 자세히 보기 링크, 텍스트 요소 3종 이하 — eyebrow가 구조(좌측 열)로 옮겨가며 상한이 4종에서 3종으로 더 낮아졌다)
2. **왜 맞는가**: 우리 제품 소개는 사양 나열이 아니라 "무엇인지 한 문장으로 아는 것"이 목적이다. 조용한 톤과 일치하고, 미출시 제품(esay)에 과장된 수치를 넣을 유인을 원천적으로 차단한다.
3. **우리 식 변형(실제 구현)**: 각 색인 행(`<article class="row">`)의 콘텐츠 블록은 `h2`(사업명) + `.desc`(설명) 2종이다. 상태 라벨은 더 이상 콘텐츠 블록 안 eyebrow가 아니라 좌측 `.status` 열로 완전히 분리됐다(2절). "자세히 보기" 링크는 아직 추가되지 않았다(0절 1항) — 추가되면 3종으로, 여전히 상한 안이다. 더 추가하지 않는다(사양 리스트·수치 금지는 유지).
4. **버린 것**: Apple의 섹션 경계(그림자 없이 배경색 전환으로 구분)는 색인 행 구조에서 `--hairline` 1px 구분선으로 대체됐다(8절에서 지각 가능성 재검토). 가로 스크롤 갤러리는 여전히 버린다.

### 1-2. (삭제) Apple — 스크롤 단계적 공개

폐기됨. 위 "폐기 항목" 표 참고. 비트리거 모션 0 원칙으로 대체됐다.

### 1-3. Vercel — 상태 표기, Badge 컴포넌트에서 구조로

1. **패턴 이름(갱신)**: 라이프사이클 상태 표기 — 당초 Vercel의 Badge 컴포넌트를 참고했으나, **최종 구현은 Badge가 아니라 좌측 열**이다.
2. **왜 맞는가**: Vercel 공식 가이드("배포 생명주기가 아닌 상태는 Badge를 쓰라")가 "상태를 색·강조 없이 중립적으로 표기한다"는 원칙까지는 유효하게 뒷받침한다. 다만 그 원칙을 구현하는 **형태**는 B안에서 더 강하게 바뀌었다 — 배지라는 장식 컴포넌트 자체를 없애고, 열이라는 레이아웃 구조로 "이것은 메타정보"라는 신호를 대신한다(2절).
3. **우리 식 변형(실제 구현)**: `.status{font-size:14px;color:var(--ink-mid);line-height:1.45}` — pill·border·배경 없음. `grid-template-columns:132px minmax(0,1fr)`로 상태를 본문과 분리된 고정폭 열에 둔다.
4. **버린 것**: Vercel의 8색 의미 매핑은 원래 명세부터 버렸다(액센트 1개뿐). 이번 갱신에서 **배지(pill) 형태 자체도 버린다** — 중립 배지 설계(구 2-3절)는 폐기 항목이다.

### 1-4. Vercel — 반응형 그리드, 적용 대상 소멸

1. **패턴 이름**: sm/md/lg 3단 브레이크포인트 그리드 정의 방식
2. **갱신**: 카드 그리드(`.tile-grid`) 자체가 폐기되고 매단 들여쓰기 색인 행으로 교체돼 **이 패턴이 적용될 대상이 없어졌다.** 사업 3개는 1열로 세로 나열되는 행이지 다열 그리드가 아니다. 실제 구현의 반응형 단계는 2단뿐이다: 기본(760px 이상, `.row` 2열: 상태 132px + 본문) / `max-width:760px`(1열 전환) / `max-width:380px`(여백·패딩 축소). 3단 그리드 명시는 적용 대상이 없어 더 이상 필요하지 않다.
3. **남아 있는 그리드**: `.about .facts`(회사 정보 4항목)는 여전히 `grid-template-columns:repeat(auto-fit,minmax(150px,1fr))`로 다열 그리드를 쓰고, `max-width:380px`에서 1열로 강제 전환된다. 이 부분에 한해 Vercel 그리드 정의 방식(브레이크포인트별 컬럼 수 명시)이 여전히 유효하게 적용돼 있다.
4. **버린 것**: 제품 소개 전체에 다열 카드 그리드를 쓰는 접근 자체를 버렸다(B안의 레이아웃 결정, 3절 레이아웃 참고).

### 1-5. Stripe — 설명형 다이어그램 (상세는 3절)

1. **패턴 이름**: 레이블·방향·단계 번호·접근성 트리 노출을 만족하는 다이어그램
2. **왜 맞는가**: 콘텐츠 자동화·알고리즘 트레이딩은 보여줄 UI가 없는 제품이다. 조건 4가지 모두 확신도 높음(WAI-ARIA 기반).
3. **우리 식 변형(실제 구현, 갱신)**: 실제 구현은 SVG 장식 레이어 없이 `<ol class="steps">` 단독이다. 레이블·방향(목록 순서)·단계 번호(`::before`의 카운터)·접근성 트리 노출(실제 HTML 목록이므로 자동 충족) 네 조건을 SVG 없이도 전부 만족한다. 상세는 3절.
4. **버린 것**: Stripe의 3단 문서 레이아웃은 여전히 쓰지 않는다. 당초 계획했던 장식용 SVG(화살표·노드 도형)도 최종 구현에서는 쓰지 않았다 — "대담함은 한 곳에만"(B안 원칙 4-1) 아래 장식을 더 걷어낸 결과로 읽는다.

### 1-6. Notion — 타이포 계층과 무테두리 구획

1. **패턴 이름**: 크기·굵기·자간의 계단식 차이 + 여백만으로 계층을 만드는 방식(채워진 테두리 박스 없이)
2. **왜 맞는가**: B안은 이 패턴을 원래 명세보다 더 강하게 충족한다. 색인 행 사이의 구분은 1px `--hairline` **선**이며, 채워진 박스나 음영 카드가 아니다. `.card`(esay 제품 화면)만 `--paper` 면을 쓰지만 테두리는 없다.
3. **우리 식 변형(실제 구현)**: 타입 스케일이 92px→44px로 대폭 축소됐다. 성명문 `clamp(30px,4.2vw,44px)` / 사업명(`.row h2`) 26px / 본문 17px / 상태·메타 14px의 4단 계단이 Notion이 관찰한 "박스 없이 크기·여백으로 구분"하는 방식을 그대로 따른다. 수치는 디자인 결정(B안)이며 Notion에서 차용한 공식값이 아니다 — 리서치팀이 원 출처(designmd.cc)를 3자 측정·확신도 중간으로 명시했다.
4. **버린 것**: Notion 특유의 숫자 포인트·카드형 분해는 여전히 가져오지 않는다(해당 자산 없음).

### 1-7. Linear — 액센트는 클릭 가능한 것에만

1. **패턴 이름**: 무채색 스케일 + 단색 액센트, 액센트는 인터랙션 요소에만 사용
2. **왜 맞는가**: B안은 이 원칙을 구조적으로 강제한다 — 잉크 스케일에 쓸 색이 텍스트용으로 하나뿐이고, `--signal`(청록)은 잉크 색상 계열 밖에 있어 액센트가 본문 텍스트의 일부로 번질 수 없다(제안 문서 1절). 확신도: 원칙 자체는 제3자 역추출 3곳 일치(중간), 적용 방식은 브랜드팀 설계.
3. **우리 식 변형(실제 구현)**: `--signal`은 `.jump a`의 hover/`.masthead nav a`의 hover/`.mail`(문의 메일 링크)/`.card .pick span.on`/`:focus-visible` 외곽선에만 쓰인다. 상태 텍스트(`.status`)·단계 번호(`.steps li::before`)·본문은 전부 `--ink`/`--ink-mid`다. 전환 시간(150~250ms 등)은 애초에 적용 대상이 없다 — 구현에 `transition` 선언이 없어 호버는 즉시 전환된다. `prefers-reduced-motion`·포커스 가시성은 여전히 Linear가 아니라 WCAG 2.3.3 / 2.4.7을 근거로 쓴다.
4. **버린 것**: "다크 톤 강조 블록"은 당초 레퍼런스 전제 오류로 폐기됐고, 이제 다크 타일이라는 대상 자체가 없어 이 논의는 완전히 소멸했다(폐기 항목 표 참고).

### 1-8. 한국어 조판 보정 — 보간식 삭제

**구 1-8절의 `clamp()` px 보간식(h1 -1.75px~-0.85px, 섹션 제목 일반화 공식 포함) 전체를 삭제한다.**

- 이유: 보간식은 92px 상한 스케일에서 92px 지점의 자간을 36px 지점보다 더 좁혀야 한다는 전제로 설계됐다. B안은 성명문 상한을 **44px**로 낮췄고, 이 범위에서는 Pretendard 공개 가이드(중간 이하 제목 0px, 리서치 확인·확신도 높음)에 그대로 들어맞아 자간을 좁힐 근거가 없어진다. 실제 구현은 성명문에만 예외적으로 `-0.01em`을 두고(제안 문서의 디자인 선택, 확신도: 설계), 사업명·본문·메타는 전부 `letter-spacing: 0`이다.
- 보간식이 풀던 문제(뷰포트 폭에 따라 자간이 선형으로 바뀌어야 한다)는 애초에 스케일이 좁아 생기지 않는다. **보정할 구간이 없으므로 보정 장치도 없다.**
- 음수 자간을 쓰지 않는다는 점은 `web.md`에 "자간에 음수값을 쓰지 않는다(44px 상한 스케일에서 필요한 구간이 없다). 예외는 성명문 `-0.01em`"로 이미 명문화돼 있다.

## 2. 자체 설계 영역 — "성숙도 위계" (좌측 상태 열로 전면 교체)

리서치팀이 명시적으로 "레퍼런스에 답이 없다. 직접 설계해야 한다"고 확인한 영역. 아래는 전부 **브랜드팀 설계(리서치 근거 아님)**이며, B안 채택으로 설계 결과물이 완전히 바뀌었다.

### 2-1. 문제의 재정의 (변경 없음)

현재 콘텐츠 자동화만 다크 타일인 이유는 "시각적 변화를 주려던 것"뿐인데, 성숙도가 다른 3개 사업을 나란히 둔 맥락에서 "이 사업이 더 중요하다"로 읽힌다(Vercel 리서치 지적, 우리 확인). 해소 원칙: **성숙도는 정보로 전달하되, 위계(크기·명도·색의 차이)로 전달하지 않는다.**

### 2-2. 결정 — 다크 타일 폐기는 더 이상 조치가 아니다

구 명세는 "다크 타일을 폐기하고 전부 동일 배경으로 통일"하는 조치를 제안했다. B안 구현은 타일 그리드 자체를 쓰지 않으므로 이 조치는 **할 일이 사라졌다**(폐기 항목 표 참고). 세 사업은 색인 행(`<article class="row">`)으로 나열되며, 배경색 차이라는 개념 자체가 없다. 행 구분은 1px `--hairline` 선뿐이다.

### 2-3. 결정 — 성숙도는 좌측 상태 열로 구분한다 (배지 pill 대체)

**배지(pill) 컴포넌트를 쓰지 않는다.** 세 사업의 상태("출시 준비 중" / "사내 운영" / "연구 개발")는 `.status` 클래스의 텍스트로, 본문 콘텐츠와 분리된 **고정폭 좌측 열**(`grid-template-columns:132px minmax(0,1fr)`)에 둔다.

이유: 색·명도로 강조 단계를 나누는 대안(필터형/윤곽형, 구 2-3절에서 검토)은 어느 쪽에 강조를 주더라도 상대적 위계가 재생산된다. **배지라는 "컴포넌트"를 쓰는 순간, 그 컴포넌트에 무게·색·테두리를 조금이라도 다르게 줄 유인이 생긴다.** 좌측 열은 컴포넌트가 아니라 레이아웃 구조이므로 이 유인 자체가 없다 — "열이라는 구조가 메타정보임을 말하므로 배지 장식이 필요 없다"(B안 제안 문서 3절).

**실제 토큰 (신규 색 토큰 없음 — 확정 토큰만 사용)**

| 속성 | 값 | 근거 |
|---|---|---|
| 배치 | 좌측 고정폭 열(132px), 본문과 `gap:40px` | 배지가 아니라 구조로 분리 |
| font-size | 14px | 확정 타입 스케일의 "메타·상태" 단 |
| line-height | 1.45 | 확정 타입 스케일(메타·상태는 1.5가 기준이나 열 안에서 약간 좁힘 — 디자인 선택) |
| color | `var(--ink-mid)` (`#45575F`, 7.55:1 on white) | 확정 토큰. 본문보다 낮은 위계임을 색으로도 암시하되, 세 사업 모두 동일 색이라 사업 간 위계는 생기지 않는다 |
| 배경·테두리·radius | 없음 | 배지가 아니므로 pill·border 자체가 없다 |
| 760px 미만 | `grid-template-columns:1fr`(1열), `.status{padding-top:0}` | 열 구조가 깨지며 상태 텍스트가 사업명 **위에** 쌓인다 — 연결이 읽히는지는 8절 실측 과제 |

색 추가가 필요해지는 경우(예: 사업 담당 본부별 색 구분)는 이번 갱신에서도 제안하지 않는다. 필요 시 별도로 브랜드팀 승인 절차를 밟는다.

### 2-4. 보조 장치 — 성숙도 암시가 "다이어그램 형태"에서 "텍스트"로 이동

구 명세는 추상 제품 2개의 다이어그램 형태(직선형/순환형)로 성숙도를 암시하는 보조 장치를 제안했다. 실제 구현에 SVG 다이어그램 자체가 없어(3절), 이 장치는 **텍스트로 실현**됐다:

- 콘텐츠 자동화(사내 운영) → `<ol class="steps">`가 1→2→3→4에서 끝난다. 추가 설명 없음 — 끝나는 파이프라인이라는 인상.
- 알고리즘 트레이딩(연구 개발) → `<ol>` 3단계 뒤에 별도 문장 `.loop`("검증 결과를 설계로 되돌려 반복합니다.")가 붙는다. 순환 구조를 화살표 도형이 아니라 **문장으로 직접 말한다.**

이것도 색이나 명도가 아니라 **내용의 구조(끝나는가, 되돌아가는가)**로 성숙도를 전달하는 방식이라 "중요도"로 오독될 위험이 낮다. 이 의미 연결은 여전히 브랜드팀의 설계적 해석이고 리서치 근거가 아니다.

## 3. 추상 제품 2개의 설명형 목록 명세 (실제 구현 반영)

Stripe 축 4조건(레이블 필수·방향 명시·단계 번호·접근성 트리 노출)을 만족해야 한다. **이 절의 핵심 원칙(아래 (b) 방식)은 시각 방향과 무관하며 절대 되돌리지 않는다.**

### 실제 구현 상태 (갱신)

최초 명세는 "SVG는 장식, 단계 목록은 실제 HTML로 나란히 노출"(아래 (b))을 제안했다. **실제 구현에는 SVG 자체가 없다.** `<ol class="steps"><li>...</li></ol>`만 존재하고, 장식용 도형·화살표가 따로 그려지지 않는다.

이것은 (b)의 원칙을 되돌린 것이 아니라 **더 단순한 형태로 만족시킨 것**이다 — SVG가 없으므로 평탄화할 대상도 없고, 중복될 콘텐츠도 없다. 시각 사용자와 스크린리더 사용자가 똑같이 `<ol>`을 보고/듣는다. (b)가 막으려던 문제(SVG `role="img"` + 내부 `<text>`의 평탄화)는 원천적으로 발생할 수 없는 구조가 됐다.

**이 원칙은 향후에도 유효하다**: 나중에 장식용 시각 요소(화살표 등)를 추가하게 되면,
- SVG는 **장식으로 남긴다**: `aria-hidden="true"`를 유지하고, `role="img"`/`<title>`/`<desc>`를 SVG에 걸지 않는다.
- `<ol><li>`가 유일한 콘텐츠 소스로 남아야 한다. 평탄화 문제를 원천적으로 피하고, 텍스트가 DOM에 그대로 있어 검색·번역·확대에도 유리하다.
- 모든 `fill`/`stroke`는 `currentColor` 또는 CSS 변수로 지정한다. 인라인 `style="fill:#000"` 금지.

**결함 3의 실제 원인 정정 (변경 없음)**: 원인은 `aria-hidden="true"` 자체가 아니라 **대체 텍스트 없이 장식만 두고 끝낸 것**이었다. 현재 구현은 장식이 없고 `<ol>`만 있어 이 문제가 구조적으로 생길 수 없다.

### 3-1. 콘텐츠 자동화 — 직선형 4단계 (구현됨)

- `<ol>` 노드: 1. 소재 입력 / 2. 에이전트 처리 / 3. 합성 / 4. 출력
- 흐름: 문서화된 순서(목록 순서) 그대로. 4번 이후 추가 설명 없음 — "반복 가동 중"이라는 인상을 문장이 아니라 **침묵**으로 전달한다(2-4절).

### 3-2. 알고리즘 트레이딩 — 순환형 3단계 (구현됨, 레이블 소폭 변경)

- `<ol>` 노드: 1. 전략 설계 / 2. 백테스트 / 3. 검증 (구 명세의 "검증·반영"에서 "·반영" 부분이 별도 문장으로 분리됐다)
- 순환: `<ol>` 바로 아래 `.loop` 문단("검증 결과를 설계로 되돌려 반복합니다.")으로 명시. 곡선 화살표 도형 대신 문장이 순환 구조를 전달한다.

### 주의 — 사실 확인 범위 (변경 없음)

위 노드 레이블은 현재 카피를 추상화한 **브랜드팀의 설명 제안**이며, 내부 운영 단계를 확정 발표하는 것이 아니다. 담당 본부가 실제 단계명과 다르다고 판단하면 교체한다. 추측으로 회사 사실을 단정하지 않는다는 원칙(CLAUDE.md)에 따라, 이 레이블들은 "설명을 위한 일반화된 용어"로 한정한다.

## 6. 확정 토큰 (CEO 확정, 2026-11-06 — 임의 변경 금지)

구 명세의 Apple 계열 회색 팔레트 + `#0066cc` + Noto Sans KR을 **아래로 전면 교체한다.** 출처는 `docs/decisions/2026-11-06-visual-direction-index.md`이며, `web.md`에 이미 반영돼 있다. 이 절은 그 표를 그대로 옮긴다 — 브랜드팀이 별도로 바꾸지 않는다.

```
--ink      #0F1C24   제목·본문        (17.33:1 on white)
--ink-mid  #45575F   보조 텍스트       ( 7.55:1 on white)
--hairline #94A3AB   선 전용           ( 2.60:1 — 텍스트 금지)
--paper    #F4F6F6   면
--page     #FFFFFF   바탕
--signal   #2E6354   링크·포커스·상태  ( 6.93:1 on white)
--measure  540px     본문 측정폭
```

- 전부 WCAG 상대휘도 공식으로 계산해 검증됐다.
- `--hairline`은 본문 대비 기준에 미달한다. **선과 구분자에만 쓴다.** → 8절에 이 규칙과 실제 코드가 어긋나는 지점 하나를 실측 과제로 올렸다(`.steps li::before`).
- 서체 2종: **고운바탕**(Gowun Batang, weight 400/700 — 성명문·사업명) + **IBM Plex Sans KR**(weight 300/400/500/600 — 본문·UI). Noto Sans KR은 더 이상 쓰지 않는다. 두 서체가 회사의 두 축(조용함/소프트웨어)을 담는다. 서체를 바꾸거나 추가하지 않는다.
- 본문: 17px / `line-height: 1.6` / `letter-spacing: 0`. **자간에 음수값을 쓰지 않는다**(44px 상한 스케일에서 필요한 구간이 없다). 예외는 성명문 `-0.01em`.
- **라운드 — 값이 바뀌었다**: 구 명세의 24px(타일)/999px(버튼)에서 **3px**로 바뀌었다. 실제 코드(`border-radius:3px`)는 `:focus-visible` 외곽선, `.card .pick span`(단어 선택 버튼), `.mail`(문의 메일 링크) 세 곳에만 쓰인다 — **상호연결 표면에만, 라운드값이 "누를 수 있음"을 뜻한다**는 원칙 그대로다. 값만 24px/999px의 "뚜렷한 라운드"에서 3px의 "거의 직각"으로 바뀌었다.
- `ch` 단위로 본문 폭을 설계하지 않는다(변경 없음, 도입 안 함).
- `text-wrap: balance`/`pretty`: **web.md는 "도입 안 함"으로 명시하나, 실제 코드에는 두 곳(`.statement h1`, `.about p`) 존재한다.** 이 불일치는 임의로 정정하지 않고 8절 실측 과제로 넘긴다 — 규칙과 구현 중 어느 쪽이 맞는지는 IT본부 확인 사항이다.

### 신규 토큰 제안

**없음.** 좌측 상태 열(2절)은 확정 토큰 6개만으로 구현된다. 색 추가는 이번 갱신에서도 요청하지 않는다.

## 7. 성능 예산 (초기 JS 150KB gzip 이하, LCP 2.5초 이하)

| 패턴 | 예산 내 가능 여부 | 비고 |
|---|---|---|
| 좌측 상태 열, `<ol>` 단계 목록 | 가능 | 순수 CSS/시맨틱 HTML, JS 비용 0 |
| 성명문 h1 LCP | 영향 있음, 재측정 필요 | 웹폰트 2종(고운바탕+IBM Plex Sans KR), `font-display:swap` 적용으로 FOUT는 즉시 보이나 2종 로딩이 LCP에 주는 영향은 8절 실측 과제 |
| 전체 | **신규 JS 라이브러리 없음.** CSS·시맨틱 HTML만으로 구현됨 | 예산 초과 위험 낮음. 실제 수치는 8절 Lighthouse 실측 과제 |

고운바탕 + IBM Plex Sans KR 2종(가중치 6단계 합산)의 실제 로딩 용량은 **1차 미확인**이라 수치를 쓰지 않는다. 구조적으로 서체 종류가 1종(Noto Sans KR)에서 2종으로 늘어난 것은 용량에 영향을 주는 방향이 맞으나, 절감/증가 효과를 숫자로 제시하지 않는다.

## 8. 프론트엔드팀 실측 과제 (갱신)

폐기된 시각 방향(스크롤 공개, 자간 clamp)에 종속된 과제는 제거했다. B안 구현을 코드로 읽고 확인한 두 가지 불일치(아래 3·5번)를 새로 추가한다.

1. **고운바탕·IBM Plex Sans KR 2종의 실제 로딩 용량과 LCP 영향 실측.** 서체가 1종에서 2종으로 늘었다 — Lighthouse/WebPageTest로 재측정.
2. **360px 폭에서 성명문(`.statement h1`)이 몇 줄로 떨어지는지 실측.** `clamp(30px,4.2vw,44px)` + `max-width:16em` + `text-wrap:balance` 조합의 결과를 실제 기기/뷰포트에서 확인한다.
3. **`--hairline`이 선 전용 규칙을 어기고 텍스트에 번진 지점을 확인·판단.** `.steps li::before{content:counter(s) ".";color:var(--hairline)}` — 단계 번호 숫자 자체가 텍스트 색으로 `--hairline`(2.60:1, 텍스트 금지)을 쓴다. 번호를 "장식적 보조 숫자"로 보는 설계 의도인지, 선 전용 규칙 위반인지 IT본부 판단 필요.
4. **좌측 상태 열이 760px 미만에서 1열로 접힐 때, 상태 레이블과 사업명의 연결이 레이블 접두어 없이도 읽히는지 확인.** 현재 DOM 순서(상태 → 사업명)만으로 연결을 전달하는데, 접힌 상태에서 시각적 구분(여백·크기차)이 충분한지 360px/600px에서 시각 검수.
5. **`text-wrap:balance` 사용 여부를 규칙과 대조해 확인.** `web.md`는 "한국어 동작 근거 없음"으로 도입을 금지하나, 실제로는 `.statement h1`과 `.about p` 두 곳에 쓰였다. 규칙을 바꾸거나 구현을 바꾸거나 둘 중 하나로 정리해야 하는 불일치다 — 브랜드팀은 어느 쪽이 맞는지 판단하지 않고 사실만 보고한다.
6. **`<ol><li>` 단계 목록이 VoiceOver/NVDA에서 순서대로 올바르게 낭독되는지** 재생 테스트.
7. **`--hairline`(2.60:1) 구분선만으로 행·섹션 경계가 충분히 지각되는지** 360px·1440px에서 시각 검수 — 대비비가 낮아 흐리게 보일 위험이 있다(구 1-1절 "섹션 경계" 논의의 후속).
8. **`--measure:540px`가 실제 화면 폭에서 체감 줄 길이로 기능하는지 확인.** 대부분의 화면 폭이 540px보다 좁아 `max-width`가 사실상 적용되지 않는 구간이 많을 수 있다 — 실제로 줄 길이가 길어지는 폭 구간이 있는지 확인.
9. **360~760px 사이 중간폭**(접힌 폴더블, 세로 iPad mini 등)에서 레이아웃 깨짐 여부.
10. **구현 완료 후 Lighthouse 모바일 프로필로 초기 JS 전송량(gzip)과 LCP 실측**, 성능 예산(150KB gzip 이하 / 2.5초 이하) 초과 시 원인 규명(7절 연계).
11. (향후 과제, 결함 1 해소 시) "자세히 보기" 링크를 추가하게 되면 탭 타겟 44×44px 기준 충족 여부를 그때 확인한다 — 현재는 링크가 없어 측정 대상이 아니다.
